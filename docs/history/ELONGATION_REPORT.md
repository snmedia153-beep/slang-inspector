# 늘임·반복 표기 복원 결과

## 1. 원인

기존 정규화는 Unicode·기호·띄어쓰기 위주여서 같은 모음을 반복하거나 마지막 받침을 늘임 끝에 붙인 표현을 놓쳤습니다. `간다아아아아아안`은 단순히 `아아아`만 줄이면 `간다안`이 남아 등록된 `간단`과 일치하지 않습니다.

이번 범위는 반복 글자 복원입니다. 완성된 일반 단어를 초성으로 바꿔 다른 은어에 연결하지 않습니다. 기존 사전의 다의어·문맥 판단을 유지합니다.

## 2. 수정 내용

- 동일 음절·초성 3회 이상 반복, 같은 모음의 `ㅇ` 음절 늘임, 늘임 끝의 받침 결합을 복원합니다. `간다아아아아아안 → 간단`, `고오오딩 → 고딩`, `고디이잉 → 고딩`, `몸사사사사 → 몸사` 등이 대상입니다.
- 복원 결과가 활성 사전·첨부 목록의 표현 또는 등록 표현의 결합·허용 조사/어미와 일치할 때만 채택합니다. 새로운 원형을 만들어 단정하지 않습니다. 이미 등록된 원래 표기는 그대로 둡니다.
- 원문은 변경하지 않고, 복원한 문자마다 원래 범위를 연결합니다. API의 `text`는 원문, `normalized`는 복원 정규화 결과, `normalizations`는 원문·복원 후보·양쪽 위치입니다. 기존 matches·tokens·문맥·OCR 상자도 원문 위치를 사용합니다.
- `간단`만 복원됐을 때는 의미를 확정하지 않습니다. `간단한 설명`은 기존처럼 정상 처리합니다. 성적·거래 등의 문맥 조합은 기존 규칙을 사용합니다. 복원에 의존하는 일치 점수는 최대 70으로 제한하며 점수는 확률이 아닙니다.
- URL·이메일·계정·인명 표기 구간은 복원에서 제외합니다. 서로 다른 줄을 합치지 않습니다. 사전 등록·삭제 후 복원 대상도 갱신합니다.
- WebUI의 텍스트 결과와 이미지 OCR 결과에 `늘임·반복 복원 후보` 영역을 추가했습니다. OCR 글자를 수정하면 이전 복원 표시도 지우고 재분석합니다.
- 문맥 모델에는 원문과 `normalized_surface`를 함께 전달합니다. 새로운 모델이나 프로덕션 의존성은 추가하지 않았습니다.
- 긴 한글 입력에서 기존 이메일 검색 정규식이 같은 단어 내부부터 계속 재시도하는 병목을 확인했습니다. 이메일 시작 경계를 지정해 동일한 주소 전체를 보호하면서 불필요한 재검색을 제거했습니다.

## 3. 변경 파일

`ELONGATION_FILES.txt`에 이번 변경·추가 파일 13개를 나열했습니다. 변경 파일 ZIP의 경로는 프로젝트 기준 상대경로입니다. 모델·DB·로그·캐시·사용자 입력·가상환경과 이전 모델 비교 보고서는 넣지 않습니다.

## 4. 검증 결과

전체 pytest **115개 통과(69.15초)**. 최종 소스를 읽기 전용으로 마운트한 Docker 테스트 환경에서 CPU 2개·메모리 2GB·네트워크 없음으로 실행했습니다. 기존 Starlette/httpx 사용 중단 예정 경고 1개가 있으며 실패는 없습니다. Ruff, Python 구문·런타임 import, JavaScript 구문, Compose 설정 검사와 실제 Docker 빌드·healthcheck도 통과했습니다.

- 실제 텍스트 UI: 사용자 예시 복원, 단독 입력에서 성적 의미/고딩으로 오인 연결하지 않음, 문맥과 함께 등장할 때 원문 강조, 정상 문장, 모바일 overflow, 콘솔 오류 확인.
- 실제 OCR UI: 기존 합성 이미지에 OCR 실행, 수동 수정 텍스트의 복원 후보, 단독 복원은 빨간 상자 없음, 문맥 추가 시 기존 상자에 연결, 수정 중 이전 결과 숨김 확인.
- 새 단위·통합 테스트: 모음·음절·초성 반복, 받침, 조사·인접 단어, NFD·이모지, 개인정보, 정상 문맥, 문단 경계, 사전 갱신, OCR 좌표, 15,003자 입력.

실제 Chromium에서 새 복원 UI·기존 텍스트 UI·기존 OCR UI 회귀 스크립트를 모두 실행했고 콘솔 오류는 없었습니다. 기존 사전은 643개이며 사전 데이터·의존성·Docker/Compose 설정은 변경하지 않았습니다. OCR 기존 합성 샘플은 최종 UI 검사에서 18단어·6표현을 인식했고 서버 처리 시간은 511.5ms였습니다.

### 합성 입력 지연

같은 PC·기존 18640 포트에서 HTTP 요청 전체 시간을 각 20회 측정했습니다. 첫 준비 요청 1회는 제외했고 GPU/LLM은 호출하지 않았습니다.

| 사례 | 변경 전 중앙값 | 최종 중앙값 | 의미 |
|---|---:|---:|---|
| 정상 문장 22자 | 4.715ms | 7.152ms | 복원 검사 비용 약 2.4ms 추가, 검토 일치 0개 유지 |
| 늘임+문맥 17자 | 4.836ms | 7.995ms | 기존에 놓친 늘임 원문을 추가로 대조 |
| 모음 반복 15,003자 | 680.240ms | 42.729ms | 이메일 재검색 병목 제거, 원문 전체 범위 복원 |

실행 중인 다른 프로그램과 네트워크·컨테이너 스케줄링 영향을 통제한 대규모 성능 평가는 아닙니다. 원본 지표는 현재 작업 폴더의 `artifacts/elongation-before.json`, `artifacts/elongation-after.json`에 있으며 합성 사례명·문자 수·시간·개수만 담았습니다. ZIP에는 소스·검증 도구·문서만 포함합니다.

## 5. 미검증 항목과 한계

복원은 사전 기반 후보이며 우회 의도나 성적 의미의 확정이 아닙니다. 알려지지 않은 원형, 임의의 자음·모음 삽입, 시각적 유사 문자, 반복과 여러 종류의 기호를 혼합한 모든 우회, 다른 줄에 걸친 복원은 지원·탐지를 보장하지 않습니다. 연속된 동일 글자 2개를 일반적으로 하나로 줄이지 않습니다.

OCR 자체가 잘못 읽은 글자를 자동으로 정답화하지 않으며 기존 수동 수정 기능을 사용합니다. 새 문맥 모델의 품질·GPU 정확도 비교나 대규모 실제 게시물의 정탐률 평가는 이번 범위가 아닙니다. 표현별 새 사실·뜻을 수집하거나 첨부 목록의 의미 데이터를 변경하지 않았습니다.

## 6. 적용 방법 (PowerShell)

현재 PC의 Docker 컨테이너에 이미 빌드·적용했습니다. 기존 주소 <http://127.0.0.1:18640/>를 새로고침하면 됩니다. 기존 포트·데이터 볼륨·OCR 준비·CPU 2개/메모리 2GB 제한을 유지합니다.

변경 ZIP을 다른 복사본에 적용하려면:

```powershell
Set-Location 'D:\Sub\slang'
Expand-Archive -LiteralPath '.\artifacts\slang-elongation-update.zip' -DestinationPath . -Force
.\scripts\Start-Slang.ps1
```

합성 입력 속도 재측정:

```powershell
python -X utf8 scripts/benchmark_elongation.py --output artifacts/elongation-measured.json
```

브라우저 회귀 스크립트는 Playwright와 Chromium이 준비된 환경에서 `node scripts/verify-elongation-ui.cjs`로 실행합니다. `NODE_PATH`·`SLANG_CHROMIUM_PATH` 설정은 기존 UI 검증 절차와 같습니다.
